# Photos de profil et informations prestataire

La demande du 20 octobre 2026 prévoit une photo de profil facultative pour les clients et prestataires. Le responsable exclut les pièces d’identité pour le moment. Aucune nouvelle collecte de pièce, reconnaissance faciale, validation d’identité ou approbation automatique du prestataire n’est activée.

Dans **Comptes → fiche du compte**, l’administrateur autorisé peut ajouter, remplacer ou retirer la photo, en indiquant un motif. Dans **Prestataires → fiche du prestataire**, le bloc **Informations prestataire / KYC** regroupe le nom affiché, le téléphone, la langue, l’état du compte, le statut de vérification existant et la photo. Les libellés sont disponibles en FR/EN. Le droit `providers.read` permet la consultation du dossier ; `accounts.manage` reste nécessaire pour modifier la photo d’un autre utilisateur. Le statut de vérification reste une information existante, sans nouvelle commande de décision.

Les images sont stockées dans le bucket privé `wafou-profile-photos`. Le profil contient uniquement `photo_path`, jamais une URL publique. L’affichage utilise une URL signée temporaire de 90 secondes. Les politiques Storage limitent l’accès au propriétaire actif et aux administrateurs autorisés ; la consultation des prestataires ne donne pas accès aux photos des autres clients. Aucun accès anonyme n’est autorisé.

L’admin accepte JPEG, PNG ou WebP jusqu’à 5 Mo à l’entrée. Il redimensionne l’image à 640 pixels sur le plus grand côté et produit un JPEG, sans recopier les métadonnées du fichier original. Le stockage limite chaque objet à 2 Mo. Les objets ont un nom unique ; l’écrasement et la suppression directe sont interdits aux sessions applicatives. Ces contrôles ne constituent pas une certification de l’identité ni une analyse antivirus.

La commande authentifiée `set_profile_photo(p_path, p_expected_version, p_profile_id, p_reason)` permet au client ou au prestataire actif de changer sa propre photo. `p_profile_id` peut être omis pour cibler son profil. Le chemin doit désigner une image déjà présente dans son dossier privé. La commande contrôle les droits, le type et la taille déclarés par Storage, la version du profil et le motif administratif ; elle trace l’opération. Une répétition identique est sans effet supplémentaire. Le profil ne peut pas recevoir directement `photo_path` par une mise à jour ordinaire.

Le futur frontend client/prestataire pourra utiliser ces mêmes capacités. Ce lot livre leur backend et les écrans admin ; il ne construit pas la PWA client/prestataire.

Retirer une photo dissocie son chemin du profil. Les anciens fichiers privés restent conservés jusqu’à validation de la politique de conservation et de purge (Q-017). La durée de conservation, une éventuelle publication aux autres utilisateurs, les règles d’éligibilité et un futur parcours de validation prestataire restent **À VALIDER**. Aucun nouveau message ni événement de notification n’est généré par une modification de photo.

Migration : `supabase/migrations/202610200011_profile_photos.sql`. Recette SQL : `supabase/tests/profile_photos.sql`. Recette navigateur : `apps/admin/tests/e2e/profile-photos.spec.ts`. Les tests utilisent des données synthétiques, sans importer de photo réelle ni modifier de compte existant.

La migration a été appliquée sur l’instance Supabase le 20 octobre 2026, après sauvegarde et vérification du catalogue de l’archive. Les six suites SQL totalisent 151 assertions réussies en transaction annulée, dont 18 pour les photos. Le contrôle après application confirme 42 tables publiques sous RLS/FORCE, trois buckets privés et aucun profil existant modifié. Les deux nouvelles commandes refusent les appels anonymes via l’API HTTP. Le test complet de restauration de sauvegarde reste à effectuer.

Validation du code : typage et build réussis, 22 tests unitaires et 27 scénarios navigateur validés. Le contrôle multipart du test photo a été corrigé puis les trois scénarios photo ont été relancés avec succès ; les 24 autres scénarios avaient passé la recette complète. Le scénario de connexion avec un véritable compte admin est ignoré faute d’identifiants de recette ; les tests d’écran utilisent des réponses API synthétiques. Les captures de la fiche service mobile et du dossier prestataire ont été inspectées. Le build signale toujours un bundle supérieur à 500 Ko ; son découpage reste une optimisation ultérieure.
